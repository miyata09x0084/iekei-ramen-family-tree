## 2. 背景と解決したい課題

解決したい課題は「家系ラーメンを食べ歩く人が、次にどの店へ行くかを根拠をもって決められない」ことです。

家系ラーメンは、どの店で修業したか、どの系統から分かれたかという系譜が味の傾向と強く結びついています。直系、壱系といった系統を知っていれば、「好きだった店の兄弟店」や「まだ食べていない系統の代表店」という選び方ができます。

現状では次の3点が障害になっています。

- 系譜の情報が個人ブログ、まとめ記事、SNSに散らばっていて、出典や更新日が分からないものが多い。
- 一般的なグルメサービスは評価点や距離で探す設計で、系譜から店をたどる導線がない。
- 自分がどの系統をどこまで食べたかを把握する手段がなく、次の一軒が場当たりになる。

既存サービスに対してこの企画が重視するのは実用性です。系譜を眺める読み物ではなく、「次の一軒が決まる」ところまでを提供します。

## 3. 目的・ゴール・成功指標

目的は、事業化までは目指さず、実際のユーザーに信頼されて使われるサービスを公開することです。コードとデータはオープンソースとして公開します。収益化は将来の選択肢として残し、初版の要件には含めません。

| ゴール | 成功指標 (案) | 測り方 |
| --- | --- | --- |
| 使われる | 公開後30日で、開発者以外の利用者が50人 | Cookieを使わないアクセス解析 |
| 次の一軒が決まる | 提案された店の詳細を開いた割合が30%以上 | 画面遷移の集計 |
| 信頼される | 系譜データの全件に出典がある。誤りの報告に7日以内で対応する | データ検証とIssueの履歴 |
| 開かれている | 公開後30日で、外部からの修正提案が1件以上 | GitHubのPull RequestとIssue |
| 続けて使われる | ログインした利用者の30%が、2店以上を記録する | 訪問記録の件数の集計 |
| 蓄積が育つ | 公開時に全店へ行く理由と出典がある。公開後30日で5店以上を追加する | データの件数と更新履歴 |

数値はすべて仮置きです。

## 4. 想定ユーザーと利用シーン

対象は家系初心者からマニアまでです。知識量によって求めるものが違うため、3つの層に分けて考えます。

| 層 | 状態 | 求めること | 主な利用シーン |
| --- | --- | --- | --- |
| 初心者 | 1〜3店を食べた。系統の名前を知らない | 系譜の全体像と、最初に押さえる代表店 | 食べた店を1つ選び、近い系統の店を知る |
| 中級者 | 10店前後を食べた。好みの傾向がある | 好きな店と同じ系統の店、未開拓の系統 | 週末に行く店を、訪問済みの記録から決める |
| マニア | 系譜をほぼ把握している | 正確で新しい情報、自分の知識の反映先 | データの誤りや新店を見つけて修正を提案する |

初版で中心に置くのは中級者です。開発者本人がこの層にあたり、15日間の開発中に自分で使って検証できます。

ヒアリングできる相手がいないため、公開後のフィードバックで層の仮説を見直します。

## 5. システム化の方向性

コンセプトは「次の一杯を、理由つきで決める」です。長く残る価値は、出典つきの公開データと、店ごとの「行く理由」の文章の蓄積に置きます。機能は真似できますが、この蓄積は真似に時間がかかります。

利用の流れは次のとおりです。

1. 開くと、次の一杯の候補3店と、それぞれの行く理由が出る。
2. 気になる候補の理由を、系譜図と出典で確かめる。
3. 行ったら「行った」の印と味メモを残す。
4. 記録をもとに、次の候補が更新される。

提案には必ず理由を付けます。例は「訪問済みの A店と同じ師匠筋」「まだ食べていない系統の源流店」です。理由が見えることが、評価点による推薦との違いであり、信頼の土台になります。

製品の中心は2つです。1つ目は「行く理由」です。店ごとに、系譜上の位置づけと、その店へ行く意味を2〜3文で書きます。事実には出典を付け、文章は独自に書きます。2つ目は味メモです。訪問時に濃さと再訪したいかを一言で残し、提案を自分の好みに寄せます。味メモは本人だけのもので、店の評価としては公開しません。制覇の演出や称号は先行アプリと重なるため初版では簡素な進捗表示にとどめます。初版の反応を見たうえで、第2版で番付のない本人だけの制覇機能として足すかを決めます。

| 観点 | 一般的なグルメサービス | この企画 |
| --- | --- | --- |
| 探し方 | 評価点、距離、ジャンル | 系譜上の関係 |
| 推薦の根拠 | 他人の評価 | 自分の訪問記録と系統 |
| データの透明性 | 運営会社が管理 | 出典つきで公開し、誰でも修正を提案できる |

家系に特化した先行サービスとして、iPhoneアプリ「[家系ラーメンマニア](https://app-liv.jp/5354757/)」があります。店ごとの系譜図、未訪問の店を絞れる地図、注文内容つきの訪問記録、制覇バッジと番付を備えた投稿SNSで、この企画と重なる部分が大きいです。以下は紹介記事 (2026年10月8日確認) にもとづく比較で、アプリ本体は未確認です。

| 観点 | 家系ラーメンマニア | この企画 |
| --- | --- | --- |
| 提供形態 | iPhoneアプリ | Webサイト。インストール不要で Androidでも使える |
| 記録の性格 | 写真つきで投稿し、共有するSNS | 本人だけの記録。投稿も番付もない |
| 次の一軒 | 地図で未訪問の店を自分で探す | 系譜を根拠に、理由つきで3店を提案する |
| 系譜の見せ方 | 店ごとの系譜図 | 提案の理由を確かめる場として、全体を1枚で見せる |
| データ | 公開状況は未確認 | 出典つきで公開し、誰でも修正を提案できる |

ほかに、チェーン店の公式スタンプアプリと、ジャンルを問わないラーメン記録アプリがありますが、系譜は扱っていません。

## 6. スコープ

初版 (MVP) は、15日・一人・月1,000円以内で公開できる範囲に絞ります。

| 区分 | 内容 |
| --- | --- |
| 初版でやる | 次の一杯の提案 (最初の画面)、店ごとの「行く理由」、系譜図の表示、店の詳細、訪問済みの記録、味メモ、データ修正の提案導線、ログイン、訪問記録の端末間同期、アカウントの削除 |
| 初版でやらない | レビューや写真の投稿、プロフィールの公開、ランキング、ユーザー同士の交流、混雑や行列の情報、ネイティブアプリ、収益化 |
| 将来構想 | 制覇の演出と称号 (第2版の候補。番付なし、本人だけに表示)、全国の店舗への拡大、「行く理由」の共同執筆、現在地からの距離を加味した提案、麺・味・油の注文の記録、収益化 |

初版のデータ範囲は30店に固定します。最終的には全国を対象にしますが、系譜データの整備が作業量の大半を占めるため、初版は件数を固定します。内訳は、源流と代表店 (神奈川・東京中心) を20店、愛知県内の店を10店とします。

## 7. 機能要件

初版の機能は12で、必須は9つです。ログインなしでも全機能を試せ、ログインすると訪問記録がアカウントに保存されます。

| ID | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| F-01 | 系譜図の表示 | 系統と店の師弟・分家関係を図で表示する。系統ごとに色分けし、拡大・縮小できる | 必須 |
| F-02 | 店の詳細 | 店名、系統、師匠筋、所在地 (市区町村まで)、創業年、行く理由、出典、最終確認日を表示する | 必須 |
| F-03 | 訪問済みの記録 | 店に「行った」の印を付け外しできる。記録は系譜図に反映される。未ログイン時は端末内に保存する | 必須 |
| F-04 | 次の一杯の提案 | 最初の画面に表示する。訪問記録と系譜から候補を3店示し、それぞれに理由を付ける。候補は都道府県で絞り込める。位置情報は使わない | 必須 |
| F-05 | 修正の提案導線 | 各店の詳細から、GitHubのIssue作成画面へ移動できる | 必須 |
| F-06 | 絞り込み | 系統、都道府県で店を絞り込める | 推奨 |
| F-07 | 系統の解説 | 各系統の特徴を初心者向けに短く説明する | 推奨 |
| F-08 | ログイン | Googleアカウントでログイン、ログアウトできる。ログイン時に端末内の記録をアカウントへ引き継ぎ、別の端末でも同じ記録を使える | 必須 |
| F-09 | アカウントの削除 | 本人の操作で、アカウントと訪問記録をすべて削除できる | 必須 |
| F-10 | 進捗表示 | 系統ごとに、訪問済みの店数と全体の店数を表示する。演出は付けない | 推奨 |
| F-11 | 行く理由 | 全店に、系譜上の位置づけとその店へ行く意味を2〜3文で掲載する。事実には出典を付ける | 必須 |
| F-12 | 味メモ | 訪問済みの店に、濃さ (濃い・普通・あっさり) と、また行きたいかを記録できる。本人だけが見られる | 必須 |

F-04の提案ルール (案) は3種類です。

- 深掘り: 訪問済みの店と同じ系統で、まだ行っていない店。
- 源流: 訪問済みの店の師匠筋にあたる店。
- 開拓: まだ1店も行っていない系統の代表店。

訪問記録が0件のときは、各系統の代表店を示します。ルールは単純な規則にとどめ、機械学習は使いません。理由を説明できることを優先します。

候補には、その店の「行く理由」(F-11) と、提案ルールにもとづく一文を並べて示します。例は「A店の店主が修業した店。A店の味の原点を確かめられる」です。味メモがある場合は、「また行きたい」を付けた店と同じ系統を優先し、理由にもそれを書きます。

| ID | 分類 | 要件 (案) |

| N-07 | 運用コスト | 月1,000円以内。無料枠で収まる構成を第一候補とする |
| N-08 | 保守性 | データの形式を自動検証し、不正なデータは公開前に止める |
| N-09 | 拡張性 | 店舗数が1,000店になってもデータ構造を変えずに済む |
| N-10 | アクセシビリティ | 系譜図を、図を使わない一覧でも読める |
| N-11 | 節度 | 訪問の進み具合は本人にだけ表示する。ランキング、連続記録、期限つきの課題など、食べる頻度を煽る仕組みは入れない |
| N-12 | 文章の品質 | 行く理由は独自に書き、他サイトの文章を転載しない。事実には出典を付ける。味の優劣や他店との比較による評価は書かない |

## 9. データ方針

未定だったデータ収集と個人データについて、次の案を置きます。

**収集方法 (案)**: 系譜データは手作業で整備し、リポジトリ内のファイル (JSONまたは YAML) として管理します。修正や追加は Pull Requestで受け付けます。データベースを持たないため、費用がかからず、変更履歴がすべて残ります。

**出典の扱い**: 店の公式サイト、公式SNS、店主への取材記事など、一次情報に近いものを優先します。出典はURLを記録し、文章は転載しません。

**行く理由の書き方**: 1店につき2〜3文で、系譜上の位置づけ (誰の弟子か、どの店の源流か) と、そこから言える行く意味を書きます。根拠は出典で確かめられる事実に限り、味の評価は書きません。文章もデータと同じライセンスで公開し、Pull Requestで追記や修正を受け付けます。

**やらないこと**: グルメサイトや他のまとめサイトからの自動収集 (スクレイピング) は行いません。利用規約と著作権の問題があり、信頼を損ないます。評価点、口コミ、写真も扱いません。

**個人データ (案)**: ログインの導入により、サーバーに個人データを保存します。保存するのはログイン用の識別子と訪問記録だけです。認証は外部の認証サービスに任せ、パスワードは保持しません。表示名、メールアドレスの公開、位置情報は初版では扱いません。公開前に、保存する項目と削除方法を書いたプライバシーポリシーを用意します。

**ライセンス**: コードは MIT、データは CC BY 4.0 とします。

保持するデータは次の5種類です。店、関係、系統はリポジトリで公開し、ユーザーと訪問記録は非公開のデータベースに置きます。

| データ | 主な項目 | 公開 |
| --- | --- | --- |
| 店 | ID、店名、系統、都道府県、市区町村、創業年、営業状況、行く理由、出典、最終確認日 | 公開 |
| 関係 | 元の店、先の店、種類 (直系・暖簾分け／修業して独立／インスパイア)、確度 (確認済み／諸説あり)、出典、最終確認日 | 公開 |
| 系統 | ID、名称、源流店、解説 | 公開 |
| ユーザー | ID、認証サービス上の識別子、登録日 | 非公開 |
| 訪問記録 | ユーザーID、店ID、記録日、味メモ (濃さ、また行きたいか) | 非公開 (本人のみ) |

## 10. 制約と技術方針

制約は4つです。

| 制約 | 内容 |
| --- | --- |
| 期間 | 15日以内に初版を公開する |
| 体制 | 開発者1名 |
| 費用 | 無料が目標、上限は月1,000円 |
| 技術 | TypeScriptを使う |
| 作業時間 | 本業を優先するサイドプロジェクトとして進める。作業は1日3時間、15日で合計45時間 |

技術方針 (案) は「静的サイトに、認証とデータベースの外部サービスを足す」構成です。系譜データはビルド時にサイトへ組み込みます。ログインと訪問記録の保存だけを、認証とデータベースを一体で提供するサービスに任せます。自前のサーバーを持たないため、費用と運用の負担を小さく保てます。

具体的な構成は基本設計で決めます。候補は、TypeScript製の静的サイト生成 (Astroや Next.jsなど)、グラフ描画ライブラリ、無料枠のある静的ホスティング (GitHub Pagesや Cloudflare Pagesなど)、認証とデータベースのサービス (Supabaseや Firebaseなど) です。各サービスの無料枠の条件は着手前に確認します。

## 11. 15日間のスケジュール (案)

15日のうち、データ整備に最も長い5日を充てます。データは開発と並行して進めます。

下の日程は、1日3時間、合計45時間の作業が前提です。

| 日 | 作業 | 完了の目安 |
| --- | --- | --- |
| 1〜2 | 要件の確定、先行アプリの確認、データ形式と「行く理由」の書き方の決定 | この文書の確認事項がすべて決まる |
| 3〜4 | 基本設計、開発環境と自動公開の準備、認証とデータベースの準備 | 空のサイトが公開URLで見え、試験的にログインできる |
| 3〜9 | 系譜データと行く理由の整備 (30店) | 全件に行く理由、出典、確認日が入り、自動検証を通る |
| 5〜7 | 系譜図と店の詳細 (F-01、F-02、F-11) | スマートフォンで系譜をたどり、行く理由を読める |
| 8〜10 | 訪問記録、味メモ、提案の画面 (F-03、F-12、F-04) | 開くと候補3店と理由が出て、印を付けると更新される |
| 11〜12 | ログイン、記録の同期、アカウントの削除 (F-08、F-09) | 2台の端末で同じ記録が見え、削除すると消える |
| 13 | 修正導線 (F-05)、プライバシーポリシー | 必須機能がすべて動く |
| 14 | 実機での確認、性能の調整、README と貢献ガイド | 非機能要件を満たす |
| 15 | 公開と告知 | リポジトリとサイトが公開される |

ログインを加えたため日程に余裕はありません。推奨機能 (F-06、F-07、F-10) は余裕がある場合だけ作り、遅れた場合は店舗数を減らします。必須機能と出典の要件は削りません。

## 12. リスクと対策

最大のリスクは、系譜データの誤りで信頼を失うことです。

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 系譜データが誤っている、または諸説ある | 信頼を失う。店に迷惑がかかる | 出典を必須にする。諸説は併記する。修正の窓口を各ページに置く |
| データ整備が15日に収まらない | 公開が遅れる | 30店に固定し、系統の代表店から入力する。遅れた場合は20店で公開する |
| 店から掲載内容への申し立てがある | 対応の負担、公開停止 | 事実と出典のみを載せ、評価や論評は書かない。削除依頼の手順を明記する |
| 閉店や移転で情報が古くなる | 実用性が下がる | 最終確認日を表示する。古いデータに印を付ける |
| 公開しても使われない | 目的を達成できない | 開発者本人が毎週使う。家系ファンが集まるSNSで告知する |
| 系譜図が複雑で、スマートフォンで読めない | 初心者が離脱する | 系統単位の表示から始め、一覧表示も用意する |
| ログインの導入で個人データを預かる | 漏えい時に信頼を失う。開発と運用の負担が増える | 保存する項目を最小にする。認証は外部サービスに任せる。本人以外が記録を読めない設定を公開前に確認する |
| 必須機能が9つあり、15日に収まらない | 公開が遅れる、または品質が落ちる | 10日目の時点で遅れていれば、ログイン (F-08、F-09) を公開後の第2版に回す |
| 先行アプリと機能が重なる | 後発として選ばれない | Web、非公開の記録、理由つきの提案、公開データの4点に絞って差別化する。SNS機能では競わない |
