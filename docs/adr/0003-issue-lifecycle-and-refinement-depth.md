# ADR 0003: issue のライフサイクルと「詰める」深さ

- 日付: 2026-09-25
- 状態: 採択

## 背景

ADR 0001 で優先順位の置き場所（GitHub Project）と列の意味を、ADR 0002 で新規 issue の自動追加を決めた。残っていたのは「Inbox の issue をどこまで詰めてから着手する順に入れるか」である。

issue に詳細設計（ファイル構成・ライブラリ・API 形）を書くと、着手までの間にコードの実態とずれる。#18 が `?shop=` 前提のまま古くなり、#29 の `/shops/[id]` と食い違った例がある。また趣味のサイドプロジェクトでは、着手前に書く量が多いほど腰が重くなる。詰まる原因は設計の不足ではなく着手の重さである。

`/idea`（調査せず即登録）というスキルが既にあり、登録の形式は定義済み。「詰める」は `/idea-refine` が担っていたが、1 問ずつ最大 3 問という方式では判断の分かれ目が多い issue（#29 の載せる内容、#2 の収録範囲）を詰めきれず、用語の揺れ（`direct` が系統と認定関係の両方を指す、系譜と系統の使い分け）も残らなかった。本 ADR は登録から着手までの全体の取り決めと、「詰める」の実体を `grilling` + `domain-modeling` に置き換える決定を記録する。

## 決定

issue は次の 5 段階を通る。

| 段階 | Project 上の状態 | 何をする | issue に書くもの |
|---|---|---|---|
| 1. 登録 | Inbox（自動） | `/idea` か任意の手段で 1 行で作る。調査しない | 原文・登録日・次の一歩（`/idea` の形式） |
| 2. トリアージ | Inbox → someday / 数字待ち / close / 3 へ | 次に触るときに行う。定期日は設けない | 数字待ちにする場合のみ、しきい値と判定日を 1 行 |
| 3. 詰める | ラベル `idea` → `enhancement` + `P1` | `/idea-refine`。中身は `grilling` + `domain-modeling`（= `/grill-with-docs`）で、根を「この issue が完了とは何か」に固定する | 背景・やること・やらないこと・完了条件。全体で 30 行以内。確定した用語は `CONTEXT.md` |
| 4. 順番に入れる | 着手する順、優先順 = 末尾番号 | 5 件上限。超えるなら 1 件を someday に落とす | なし |
| 5. 着手 | ブランチと PR | `/grill-with-docs` で「どう作るか」のツリーを詰めてから Plan モード | issue には書かない（下記） |

**トリアージの基準（2 軸）**

- 作った後の手間が増える、または楽しくない → someday か close
- 数字を見ないと決められない → 数字待ち。しきい値と判定日を書けないなら someday
- それ以外 → 3 へ

**「詰める」の合格ライン**

完了条件が第三者に手で確認できる形で書けていること。書けない issue は目的が曖昧なので、着手する順に入れない。

**「詰める」の進め方（`grilling` + `domain-modeling`）**

- 今決められる問いをまとめて 1 ラウンドで出し、各問に推奨回答を付ける。「お任せ」は推奨回答を採用する
- 枝に含めるのは目的・範囲・やらないこと・完了条件・依存・数字待ちの判定条件。ファイル配置・ライブラリ・API 設計・実装手順は枝から外し、候補に出たら「未定（着手時に決める）」と書く
- 事実（コードの現状、既存 issue）はサブエージェントが調べ、ユーザーには決定だけを聞く
- 用語の揺れはその場で指摘し、確定した語はリポジトリ直下の `CONTEXT.md`（用語集）に書く。`CONTEXT.md` は用語集であり、決定や実装の詳細は書かない
- ラウンドの上限は設けない。「どう作るか」を枝から外していれば 2〜3 ラウンドで空になる

**issue に書かないもの**

実装方針・ライブラリ・ファイル配置・API 設計。これらは着手時に決め、次の 3 か所に置く。

| 置き場所 | 何を置く | 寿命 |
|---|---|---|
| `/grill-with-docs` → Plan モード | 手順・ファイル構成・作業順 | 使い捨て |
| ADR | 戻しにくい・驚く・本物のトレードオフの 3 条件が揃う判断だけ。0004 以降は 1〜3 文の軽い書式（代替案は残す価値があるときだけ節を足す） | 永続 |
| PR の説明文 | 実装の要点と確認方法 | コードと同じ |

**例外: 成立するか不明な技術点**

設計を紙に書く代わりに、30 分を上限とした検証（spike）を先に行い、結果を issue に 1 行足す。例: #30 の「静的出力で `opengraph-image.tsx` がビルド時生成できるか」。

## 検討した代替案

| 案 | 見送った理由 |
|---|---|
| issue に詳細設計まで書く | 着手までに陳腐化する。書く量が着手の障壁になる |
| Issue テンプレートを必須にする | `/idea` の 1 行登録が止まる。形式は `/idea-refine` が担う |
| `/idea-refine` を無くし `/grill-with-docs` を直接使う | issue の読み込み、「どう作るか」を枝から外す境界、4 項目での書き戻しとラベル変更の 3 つが宙に浮く。ラベル変更は「`idea` のままでは着手する順に入れない」というゲートの実体なので、薄い皮として `/idea-refine` を残す |
| `/idea-refine` の 1 問ずつ最大 3 問方式を続ける | 判断の分かれ目が多い issue を詰めきれない。用語の定義が残らない |
| `needs-triage` / `ready-for-agent` の状態機械（triage スキル） | 1 人運用には重い。外部からの issue や PR が増えたら再検討する |
| issue ごとに `docs/design/*.md` を作る | 設計文書の保守という継続運用が生まれる |

## 結果

- issue は最大 30 行に収まり、読めば「何を・どこまで・どうなったら完了か」が分かる
- 「どう作るか」はコードと同じ PR に残り、issue と実装がずれない
- 手作業は「Inbox を見て振り分ける」と「`/idea-refine` のラウンドに答える」の 2 つだけ
- 用語集 `CONTEXT.md` が issue を詰めるたびに育つ。README の凡例や店舗ページの説明文に流用できる
- 列の移動は Project 上のドラッグで行う。優先順の番号は列に入れた時点で末尾番号を付け、並び替えたときだけ振り直す
